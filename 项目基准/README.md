# 项目基准

> 本项目所有开发、设计、文档、测试工作均以此目录为准。
> 规范未覆盖之处，先在此补充规范，再动手实现。

## 使用方式

1. 开发前先查对应规范，没有规范则先补；
2. 并行开发时，每人认领**独立文件**，避免同时修改同一份；
3. 规范变更必须在对应规范的"变更记录"中登记；
4. 所有规范遵循统一的[文档模板](#文档模板)。

## 规范状态

每份规范顶部必须标注状态：

| 状态 | 含义 | 能否实施 |
|---|---|---|
| 草案 | 初稿，随时调整 | 仅供讨论 |
| 评审中 | 待确认 | 暂不实施 |
| 已确认 | 已通过 | 必须遵循 |
| 已废弃 | 不再使用 | 仅保留记录 |

## 并行开发规则

1. 每人认领独立文件，不交叉修改；
2. 组件、接口、UI 三组并行时，先冻结共享字段与命名；
3. 依赖他人的字段时，以对方规范为准，发现冲突先改规范；
4. 临时方案必须标注 `临时方案：原因 + 预计清理日期`；
5. 不在代码注释里定义规则，规则必须回到本目录。

## 文档模板

> 所有规范文档均使用以下结构，保持简洁、完整。

```markdown
# 规范名称

> 状态：草案 / 评审中 / 已确认 / 已废弃

## 目的
一句话说明为什么需要这条规范。

## 适用范围
哪些页面、组件、模块必须遵守。

## 规范内容
- 条目式列出规则
- 每条只讲一件事
- 必要时给出正确 / 错误示例

## 示例
正确的写法或实现。

## 禁止事项
明确不允许的做法。

## 关联规范
列出依赖或被依赖的其他规范文件。

## 变更记录
| 日期 | 变更内容 | 修改人 |
```

## 需求与问题记录模板

> 新增功能、发现问题、修复任务均使用此结构，统一编号便于追踪。

```markdown
## 编号：REQ-001 / BUG-001 / TASK-001

- 类型：需求 / 缺陷 / 任务
- 状态：待确认 / 进行中 / 已完成 / 已驳回
- 提出人：
- 提出日期：
- 优先级：P0 / P1 / P2 / P3

### 描述
一句话说清问题或需求。

### 现状
当前是什么样，或当前为什么做不到。

### 期望
应该变成什么样。

### 验收标准
- 可逐项勾选的验收条件

### 关联规范
涉及修改的项目基准文件。

### 变更记录
| 日期 | 变更内容 | 修改人 |
```
